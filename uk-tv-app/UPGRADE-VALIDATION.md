# UK Television upgrade validation — 22 October 2026

## 0.6.1 picture recovery and responsiveness

The user reported GB News audio without video and general sluggishness. Initial playback worked, but the final manual channel-change/full-screen check reproduced a black picture. A new generated-video regression then reproduced the exact transition failure: the changed channel rendered zero frames while its decoder and audio ran. Moving the native PlayerView with Compose movable content while replacing its player could leave the video surface detached. The fix creates and releases native views at each destination and each player change while retaining the playback engine. YouTube retains its movable page/session. Device logs also showed memory pressure and long UI frames; the old recovery watchdog stopped monitoring picture progress after the first rendered frame.

The player now checks rendered frames throughout direct playback. Six seconds without video progress while playing triggers same-channel fallback, including when audio continues. Pausing or buffering does not trigger this new check; the existing buffering watchdog remains separate. Backup ranking uses recent observed health before source priority, while the initial default/pinned selection and every source candidate are retained. Buffer allocation is bounded to 24 MiB with a 15–30 second target and one-second initial playback threshold. This is a player buffer target, not a total app memory limit.

Performance changes move programme grouping off the UI thread, cache guide and VOD derived lists, avoid scrolling/recomposing unaffected guide rows on every keypress, precompute normalised title keys, skip launch refreshes younger than fifteen minutes, and use HTTP ETags to avoid reparsing/replacing unchanged guides. Artwork refresh is associated with successful snapshot downloads and retries failed bundles, including after an HTTP 304.

The source passes 49 Kotlin tests; both debug and normal-runtime builds pass Android lint. Three device scenarios are verified on AFTSS / API 28: the new channel-change/full-screen test failed before the surface correction with zero rendered frames and passes afterwards; deliberate audio-only playback automatically recovered in 7.944 seconds, while an eight-second pause retained its source; real GB News recovered from an unavailable first source and sustained twenty seconds. The live test initially missed the extremely fast failed source between observation samples, so its assertion was corrected to use the engine's actual attempt count; its rerun passes in 30.738 seconds. All eleven built-in GB News alternatives remain. These checks cover decoder progress loss and native display handover, not every possible provider outage.

Startup measurement before optimisation was 6.063 seconds (`am start -W` ThisTime). Ahead-of-time compilation alone reduced a subsequent 0.6 launch to 1.938 seconds; the initial 0.6.1 debug launch measured 2.251 seconds. The final normal-runtime build after compilation measured 1.400 seconds (TotalTime 1.219 seconds). These are individual device observations with different cache/system conditions, not a controlled benchmark or evidence that the source changes alone explain the reduction. The final debug-runtime guide sample still had a 400 ms median frame and 1.05 second 90th percentile during a short rapid-key sequence. Switching the same code/package to the non-debuggable `tvPreview` runtime reduced those observations to 129 ms and 650 ms. These small samples are directional, not a formal benchmark; occasional UI pauses remain. The non-debuggable build retains the local debug signing certificate, app identity and data. R8 optimisation is not enabled in this update.

The normal package is updated in place to **0.6.1-preview, code 7** using the same signing identity. Its 0.6 APK and a verified 1,475-file data archive were retained before the update. No app data was cleared. All existing preference keys/values matched the pre-update backup before switching runtime builds. The updated VOD library loaded 657 titles and its Action filter displayed 150 matching titles. The user-confirmed icon and existing home favourite are retained. TiviMate and the duplicate candidate app had already been removed at the user's request.
