This review covered the Android source and merged APK manifest, embedded web players, native media requests, imported playlist handling, artwork extraction, local storage settings, the app's own Kodi bridge and resolved Android libraries. It is a source review with local regression tests, not a device penetration test or certification of third-party websites/add-ons. Findings below describe code risks; they are not evidence that the device was compromised.

## Findings and changes

| Finding | Practical risk before this update | Local remediation |
|---|---|---|
| Kodi pairing secret sent as a bearer token to a local TCP port | Another installed process occupying that port could collect the token or impersonate the engine. An unexpected redirect could also leave the intended endpoint. | HMAC-SHA256 requests and replies, bound to method/path/body and a fresh nonce; 60-second timestamp window and bounded replay cache. The pairing secret is never sent. Replies are verified before parsing. Redirects are refused. |
| Kodi could re-import a token from shared storage | A newly created shared provisioning file could overwrite the established private pairing. | Existing private token is authoritative. First provisioning uses exclusive creation and mode 0600; token length/characters and regular-file/symlink checks are enforced. No token rotation or data clearing. |
| Slow local HTTP requests could stall the bridge | Single-threaded handling without a per-connection deadline allowed unauthenticated incomplete requests to block normal requests and idle shutdown. | Loopback-only binding retained; at most four request workers, three-second inactivity and absolute deadlines, strict Host/Origin/framing checks, 4 KiB bodies, JSON-object requirement, 2 MiB reply limit and no-cache responses. Provider exception strings are no longer returned. |
| Provider pages could supply unsafe native VOD destinations | Checking only the initial HTTPS URL did not cover private addresses, DNS results, redirects or child HLS resources. Full page URLs were used as Referer headers. | A dedicated VOD HTTP client validates each request/redirect before connecting and rejects private/reserved DNS answers. Native HLS requests use the same client. HTTPS/443 only; origin-only Referer; credentials stripped on redirects. Native catalogue downloads use this policy too. |
| Inconsistent WebView URL boundaries | Main-frame allowlists did not consistently cover frame/resource URLs or ambiguous authorities. | Shared URI checks reject credentials, nonstandard ports, ambiguous authorities, unsafe schemes and explicit local destinations. Main provider host allowlists retained. File/content access, mixed content, downloads, file pickers and permission grants are disabled; Safe Browsing requested where supported. **WebView interception is a partial boundary, not a complete network firewall.** |
| YouTube exposed a Java object to all frames | Embedded frames could call player-state methods and spoof/spam status. The exposed methods were limited; this was not demonstrated arbitrary-code execution. | Removed `addJavascriptInterface`; app polls a bounded event queue in its own main document, validates event types and stops with the player. Android documents the all-frame exposure of native bridges. [Android guidance](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges). |
| Oversized inputs and unsafe media headers | Crew response truncation occurred after reading the entire body. Skipping unexpected ZIP entries could inflate them outside the extraction budget. Media header input accepted routing/framing fields and control characters. | Bounded streaming reads; immediate rejection of unexpected artwork entries; bounded header names/values and rejection of CR/LF and hop-by-hop/routing overrides. Live native playback uses an HTTP-only data source, preventing manifests from selecting local file/content sources. YouTube lookalike hostname classification also fixed. |
| Backup policy on newer Android versions | `allowBackup=false` alone does not consistently exclude device transfer on Android 12+. | Explicit exclusions for all app-data domains in cloud backup and device transfer, in addition to existing backup opt-out. [Android backup documentation](https://developer.android.com/identity/data/autobackup). |
| jsoup 1.18.3 matched two published advisories | OSV identified XML namespace memory exhaustion and a custom HTML-cleaner issue. Searches found HTML parsing, not calls to the affected XML/custom-cleaner features; exploitability in this app was not established. | Upgraded to 1.23.2 and reran catalogue parsing tests. [XML advisory](https://github.com/advisories/GHSA-65r4-943x-97jj), [cleaner advisory](https://github.com/advisories/GHSA-pmhh-3w7g-xqp8), [patched release](https://jsoup.org/news/release-1.23.2). |

## Verification

- 78 Android/JVM tests passed, including malformed provider URLs, private/literal IPs, private/mixed DNS answers, blocked redirects before transport, valid CDN redirects, header injection, bounded reads, ZIP extraction, bounded YouTube events and real loopback HTTP bridge-client tests.
- 18 Python tests passed, including normal catalogue behaviour, shared-token overwrite resistance, authenticated requests/replies, replay/body/route/expiry rejection, partial requests, slow body trickling, duplicate framing and loopback-only binding. Kotlin/Python use matching fixed HMAC test vectors.
- `testDebugUnitTest lintTvPreview assembleTvPreview assembleDebugAndroidTest` succeeded. Lint: zero errors, 73 warnings; these include existing TV layout/localisation/API warnings. Instrumentation APK compiled but **no device tests ran**.
- OSV queried 98 resolved libraries from the `tvPreview` build metadata. Before: two jsoup advisories. After: no matching advisories in the returned results. This is version matching against the available database, not proof of vulnerability-free dependencies, and excludes the installed OS/WebView/Kodi/Crew dependencies. [OSV API](https://google.github.io/osv.dev/api/).
- Current tracked-source pattern scan found no private-key, GitHub-token, AWS-access-ID or Google-API-key patterns. Two existing JWT-shaped Brightcove stream URL values were identified in channel seed files. Their upstream authorisation/provenance was not established; they were not printed, rotated or removed. This limited scan is not a full secret or Git-history audit.
- APK identity is `com.commercialoutcomes.uktelevision.preview`, version `0.9.2-preview`, code 14, non-debuggable and backup-disabled. Signature verification passed; the existing signer and approved icon are unchanged. Bundled channel catalogue, artwork and Tubi controls match the prior 0.9.1 delivery byte-for-byte. No stream alternatives were removed.
- Merged-manifest inspection found internal playback/catalogue activities unexported; the launcher is exported. Library-exported jobs/diagnostic receivers require Android `BIND_JOB_SERVICE` or `DUMP` permissions. No camera, microphone, location or shared-storage permission is requested. WorkManager adds wake-lock, boot and foreground-service permissions.

## Remaining risks and limits

1. **Third-party web players remain third-party code.** JavaScript, provider cookies, adverts and remote player/CDN code remain necessary for these integrations. WebView callbacks do not intercept every networking mechanism or every redirect, and do not control DNS resolution. The strict public-address/DNS guarantee applies to the dedicated native VOD client, not all WebView traffic. In-app controls cannot certify a provider or prevent every tracking/exploit technique.
2. **Kodi add-ons run within Kodi's permissions.** The signed bridge protects communication with other processes; it cannot isolate malicious code already running inside Kodi or holding its private token. Shared-storage add-on code, Kodi/Crew updates and third-party resolver dependencies were not audited or modified. The replay cache lasts for the service process; fresh nonces and the timestamp window also limit replay. HMAC authenticates loopback messages; it does not encrypt media links.
3. **HTTP remains enabled for existing live feeds and local Kodi.** HTTPS is enforced for internet web players and native VOD, but global cleartext blocking would break existing live sources and user-imported LAN playlists. Direct live/Crew requests may still use provider headers, including cookies, with their media/CDN chain. Those providers and user imports remain trusted for that purpose. The existing Strict Privacy option was not switched on automatically.
4. **The device itself was deliberately not inspected.** Current Fire OS/WebView/Kodi patch levels, wireless-debugging exposure and actual runtime Safe Browsing support still need checking when viewing has finished. No device-wide assurance is made.
5. **Signing/distribution is still the existing private preview arrangement.** The APK is non-debuggable but uses the existing local debug signing identity, preserved for a safe in-place upgrade. No key was regenerated or uploaded. CI uses version-tagged actions and is not a reproducible, independently attested supply chain. This review did not establish a production update/signing service or scan full Git history.
