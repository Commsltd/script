# UK Television efficiency, reliability and security audit

**Date:** 25 October 2026. **Target:** locally built 0.9.8-preview / versionCode 20, source commit `97cf360`. **Outcome:** the recent memory improvements are useful, but the app still has high-priority efficiency and recovery defects and a release-validation gap. This is an audit, not a certification or a claim that every channel plays.

No app code, Firestick settings, playback or installed packages were changed during this review. All findings below remain open. Prior installed fixes are distinguished from audit recommendations.

## Priority findings

### 1. High — hourly refresh can redownload the entire artwork bundle

`Data.kt:245–249, 276–282` and `ArtworkStore.kt:42–63, 73–98` use the catalogue build timestamp to decide whether to fetch artwork. The publisher generates a new timestamp every run. The artwork request has neither `If-None-Match` nor a content-hash comparison, even though the server supplies an ETag.

The current archive is **69,148,202 bytes (65.9 MiB)**. Each successful refresh can download, unpack, rename and delete the whole bundle even when its contents are unchanged. If hourly work runs continuously, this is roughly 1.66 GB of artwork transfer per day, before guide/stream traffic. This is potential traffic derived from the code, not measured device bandwidth. The guide list remains referenced while artwork refresh runs, and fresh programme information waits for that work.

**Recommended correction:** publish an artwork content hash, skip unchanged archives, support conditional requests, reuse unchanged content-addressed files, and decouple artwork from guide activation. Keep the last working bundle on error. Verify that an unchanged hourly refresh transfers no artwork body and does not delay programme updates.

### 2. High — incremental JSON parsing still retains the full imported guide

`Data.kt:147–174, 225–230, 276–282` collects every programme into an `ArrayList` before importing it. Streaming eliminated the earlier whole-file string/tree duplication, but the entire new programme set still coexists with the old UI cache and playback buffers. `chunked(500)` partitions that already allocated list; it is not a streaming import.

The current live catalogue contains **59,836 programme records and 29,627,511 uncompressed bytes**. The new UI window significantly reduces its resident records, but does not bound this refresh peak. A parser-only JVM test with a 128 MiB heap does not measure Android's simultaneous player, WebView, graphics and database load. No new out-of-memory crash was reproduced in this audit.

**Recommended correction:** parse into a staging database/table in bounded batches, validate the completed snapshot, then activate it atomically; retain the old snapshot on failure. Add per-record/string/source limits before allocation. Measure peak PSS, Java heap and response latency during refresh with video playing, not only during isolated parsing.

### 3. High — a renewed address can remain marked as already tried

`Playback.kt:314–317` merges fresh source objects into `candidates` during background checks without reconciling `tried`. `startNext()` filters by source ID at lines 115–119. Its final refresh compares new sources against the already updated candidates at lines 133–142.

Concrete sequence: national source A fails; regional B plays; the background inventory replaces A's expired URL with a renewed URL under the same ID; B later fails. A is still in `tried`. At exhaustion, the renewed URL already exists in `candidates`, so `changedIds` is empty and A never receives an attempt in that playback generation. The same risk applies when the playing source's URL is renewed in the background.

**Evidence level:** source-state walkthrough of these transitions, saved in the audit evidence; not an end-to-end Firestick reproduction.

**Recommended correction:** track attempted address identities (URL, headers and kind), or clear tried/health/probe state for changed identities at every merge. Preserve independent alternatives, prevent repeated retries of identical URLs and keep healthy playback undisturbed. Add a controller-level regression test for this sequence.

### 4. High — GitHub builds and smoke tests do not cover the installed release

[Remote build configuration](https://github.com/Commsltd/script/blob/344c73fc00531682e00c87af0d2ec769ba4b75eb/uk-tv-app/app/build.gradle.kts) still declares **0.3.0 / code 3**, whereas the installed local release is **0.9.8 / code 20**. GitHub's latest listed release is also a 0.3.0 preview. Consequently, its successful smoke check does not validate the current memory, VOD or recovery implementation.

The inspected 0.9.8 APK also bundles an older **332-channel catalogue dated 22 October**, while the online catalogue has 1,049 channels. Existing installations retain their downloaded database, but fresh/offline installations start with different content. This audit confirmed the asset under AAPT's `assets/catalogue.json` name; it is present, not missing.

**Recommended correction:** reconcile the reviewed app source and build workflow in a dedicated release change; create an immutable release commit/tag, regenerate and validate required assets, build once, smoke-test that exact APK and publish its hash. Add assertions for versionCode, non-debuggable flags, signer, required assets and catalogue freshness. Do not blindly push the local branch or rotate the signing key; both have compatibility consequences.

## Medium-priority findings

### 5. Background screens retain guide work and some VOD resources

`TvModel.kt:136–169` collects Room data and performs refresh work in `viewModelScope`, without foreground subscription control. `MainActivity.onStop()` releases playback but neither unsubscribes the guide collector nor clears its cached schedule. The activity may remain in the back stack during VOD browsing. This means guide imports can trigger grouping/allocation for a hidden screen while VOD uses memory.

`VodPlayerActivity.kt:340–342` pauses Tubi controls, native playback and the WebView, but Plex consent polling and other handler work are stopped only on destruction. Native VOD playback hides and pauses HTML video but retains the web document alongside the native renderer (`NativeVodPlayback.kt:84–92`). Retaining it supports fallback, but costs memory and does not establish that provider scripts/timers stop.

**Recommended correction:** use lifecycle-aware subscription and explicit stop/resume hooks; release or trim disposable guide and web caches when hidden; use a measured low-memory policy for web-to-native handoff. Preserve playback position and remote focus on return. Android recommends lifecycle-aware collection and releasing unneeded resources: [coroutines/lifecycle guidance](https://developer.android.com/topic/libraries/architecture/coroutines), [memory guidance](https://developer.android.com/topic/performance/memory).

### 6. Public live-stream probes have weaker destination checks than native VOD

`LiveSourceRefresh.kt:47–51` accepts HTTP/HTTPS hosts without rejecting private destinations. `SourceChecks.kt:119–145` follows redirects and HLS child URLs without the public-address/DNS policy enforced by `PublicVodHttp`. Each HLS child starts a new fetch with the original headers (`SourceChecks.kt:89–99`), resetting the host comparison; credential headers could consequently be sent to a different child host if such headers are supplied.

**Threat condition:** a malicious/compromised upstream playlist, or modification of an unencrypted playlist, could induce background requests to local services. The current catalogue has **29 HTTP routes** and **zero routes carrying Authorization/Cookie headers**, so credential leakage was not observed. This is a policy gap, not evidence of compromise. User-imported LAN playlists are a separate, deliberately supported use case.

**Recommended correction:** separate public built-in feeds from explicit user LAN feeds; validate destinations, DNS results, redirects and child resources for the public-feed class. Scope credential headers to their permitted origins across the whole HLS chain. Retain required HTTP feeds through an explicit compatibility policy rather than removing alternatives wholesale.

### 7. Distribution and supply-chain hardening are incomplete

The normal APK is non-debuggable and its signature verifies, but it is signed by the existing **Android Debug** identity (`build.gradle.kts:38–43`). This is not the same as a debuggable application, and the key is not alleged to be public; it does mean production key protection/recovery procedures have not been established. GitHub Actions use mutable version tags, and no dependency lock/verification metadata was found for the app build. R8 optimisation is also disabled.

**Recommended correction:** establish protected signing-key backup and controlled release access while preserving the installed signing identity; pin Actions to reviewed full commit SHAs, enable dependency verification/locking and record artifact provenance. Evaluate R8/baseline profiles only with playback and reflection regression checks. GitHub identifies full commit-SHA pinning as its immutable action-reference option: [secure Actions guidance](https://docs.github.com/en/actions/reference/security/secure-use).

### 8. Stream refresh needs operational visibility and broader tests

`LiveSourceRefresh.kt:100–112` swallows update failures and keeps the old inventory, which is a useful fallback but leaves no last-success/failure status visible. It downloads/parses approximately **976 KB** of status JSON at most every five minutes, without ETag support, and parses the JSON twice to retrieve its timestamp. Cached probe results key on source ID and network, not the URL/header identity, so a changed address can inherit a stale result for up to five minutes.

Current checks sample playlists/media for alternatives to the channel being watched. They do **not** decode-test every channel nightly, guarantee sound/picture or automatically discover a replacement for every dead static feed. This distinction should remain explicit in product status and reports.

**Recommended correction:** conditional inventory downloads, a single parse, address-aware health keys, a bounded last-refresh/error diagnostic and regression coverage for changed URLs, VPN changes, cancellation and stale inventories. Add provider-specific source renewal and server-side sample monitoring where appropriate; keep device/VPN-dependent failures separate from server probe results.

## Existing safeguards confirmed

- Incremental catalogue parsing, bounded decompressed input, validated channel/programme references, transactional guide replacement, cached-data retention on ordinary refresh errors and bounded native player buffers.
- Non-debuggable installed-build configuration; backups/device transfer excluded; internal activities unexported; no camera, microphone, location or shared-storage permissions requested by the app manifest.
- Web players disable file/content access, mixed content, downloads and native permission grants; main-frame provider restrictions remain. No `addJavascriptInterface`, trust-all TLS manager or SSL-error bypass was found in the reviewed app source.
- Native VOD validates public HTTPS destinations and DNS answers, limits redirects and removes credentials on redirects.
- The local Crew bridge signs requests and replies, rejects redirects and replays, bounds bodies and binds locally; its tests passed. This does not audit Kodi or third-party add-on code running inside Kodi.
- WebView filtering remains a partial boundary: callbacks do not cover all network mechanisms/DNS, and Safe Browsing is enabled only when supported. The device's current OS/WebView security patch state was not inspected. [Android WebView guidance](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges).

## Verification and evidence limits

- Fresh local run: **92 JVM app tests**, **68 catalogue tests**, **20 bridge tests**, all passing. Android lint: **zero errors, 75 warnings**; most concern UI text/style and API usage. Passing tests do not cover all defects above.
- Fresh [OSV](https://google.github.io/osv.dev/api/) batch lookup of **100 resolved Maven coordinates** returned **no matching advisories**. This is database version matching, not a guarantee of safe dependencies, and excludes Fire OS, WebView, Kodi and external websites/add-ons.
- APK signature verified; SHA-256: `5bbc9fb5d9ed668cb75af381f76c601a3892ee280e549adf72a1abd7b9802c0a`.
- Evidence in `/private/tmp/uk-tv-on-demand/.local/audit-2026-10-25/`: dependency results, lint summary, fresh test logs, APK metadata/signature, live catalogue/archive sizes and the renewed-source state walkthrough.
- No Firestick interaction, network attack, playback switching, installation, long-duration soak test or current device memory profiling was performed in this audit. Previous read-only device observations are background context, not fresh audit measurements. No claim of active compromise or a newly reproduced crash is made.
- An unused `VodWebCatalogue.fetch` helper parses HTML on the main thread, but no caller exists in the reviewed source. It was not classified as a demonstrated current slowdown.

## Recommended order

1. Fix artwork caching and stage/batch guide imports; establish playback-plus-refresh memory measurements.
2. Correct renewed-address attempt/probe identity handling and add regression coverage.
3. Reconcile release source/assets/CI so the tested artifact is the installed artifact.
4. Apply lifecycle cleanup and public-feed network boundaries, then complete signing/provenance and operational diagnostics.

These changes should be prepared and tested locally before any device update. Preserve channels, independent alternatives, favourites, lists, pairing state and the existing signer throughout.
